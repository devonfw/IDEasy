= Docker Sandbox for AI Coding Agents

[WARNING]
====
*This solution is experimental and targets technically skilled users only.
Use at your own risk. No warranty or support is implied.*
====

== What it is

The link:sandbox.adoc[IDEasy sandbox principle] isolates projects as folders on
your hard drive - a container is *not* involved. This page describes an
*optional, containerized variant* for AI-assisted development: it starts an
isolated Docker container containing an **automatically provisioned IDEasy
workspace** (IDEasy + an AI coding agent already installed) and runs the agent
against your git repository.

The goal is to let AI coding agents such as *Claude Code*, *GitHub Copilot CLI*
or *OpenAI Codex* safely perform development tasks, execute tests and prepare
commits/pull requests **without affecting the host environment**.

The implementation lives in the `docker-sandbox/` folder of your **settings
repository**, which IDEasy clones into `$IDE_HOME/settings` (the default settings
repository is https://github.com/devonfw/ide-settings[devonfw/ide-settings]). The
launcher therefore resolves from `$IDE_HOME/settings/docker-sandbox`. Keeping the
implementation in the settings repository lets projects using IDEasy customize the
sandbox (base image, extra tools, agent configuration) by forking their settings
repository and pointing at it with `IDE_SETTINGS_REPO`, without forking IDEasy. The
folder contains:

* `Dockerfile` - provisions the IDEasy workspace (IDEasy + agent) into an image.
* `docker-sandbox.sh` - the host launcher that builds the image, passes your Git
  identity, mounts your repository and starts the agent.
* `entrypoint.sh` - activates the IDEasy environment and runs the agent.

You can also run it directly through the IDEasy commandlet
`ide docker-sandbox`, which forwards all arguments to the launcher (see the
link:cli.adoc[commandlet reference]).

=== What you get

* An isolated container pre-loaded with a *provisioned IDEasy workspace*
(IDEasy + Claude Code installed at image build time).
* Your git repository *bind-mounted read-write _into_ that workspace as
a subfolder*, so the agent works inside a complete IDEasy-managed
workspace and its edits and `git commit` operate on your real
repository.
* A *container-local IDEasy runtime* that is discarded on exit - the
host IDEasy installation is never touched.
* Your *host Git identity* passed in, so commits are authored by you.
* *Host SSH keys / agents are NOT mounted* into the container.

== How it works

The launcher mounts *only* your git repository, and it mounts it **into** the
container's IDEasy workspace as a *subfolder* - not as the workspace root. This
keeps the container's workspace a complete, IDEasy-managed workspace:

.Mount points
[cols="asciidoc,asciidoc,asciidoc",options="header",grid="cols"]
|======================
| *Host path* | *Container path* | *Purpose*
| Your git repository (e.g. `~/…/workspaces/main/IDEasy`) | `/projects/sandbox/workspaces/main/<repo>` |
The working directory for coding tasks (read-write, so commits/PRs operate on your
real repository).
| (nothing - built into the image) | `/projects` (`$IDE_ROOT`) |
The provisioned IDEasy project. Its `conf/`, `software/` and `_ide/` are
**container-local** and discarded on exit - the host IDEasy installation is
never touched.
| Optional `--ca-cert <file>` | `/ca/certs/ca-bundle.crt` |
Corporate CA bundle, exported as `NODE_EXTRA_CA_CERTS` for trust.
|======================

The agent is started with its working directory set to the mounted repository,
inside the activated IDEasy environment.

Because only the repository is bind-mounted and the IDEasy runtime is
container-local, running an `ide install` or other tooling inside the sandbox
**does not affect the host** IDEasy installation.

== Prerequisites

* A running container engine. IDEasy recommends https://rancherdesktop.io/[Rancher
  Desktop] (see link:docker-desktop-alternative.adoc[Docker Desktop
  alternative]); https://podman.io/[Podman] is also supported.
* https://git-scm.com/[Git] with a configured `user.name` and `user.email`
  (used to pass your identity into the container).
* A checkout of the repository you want to work on.

== Quick start

Run the launcher from inside the repository you want to work on:

[source,bash]
----
bash "$IDE_HOME"/settings/docker-sandbox/docker-sandbox.sh
----

This starts *Claude Code* (the default agent) inside the container, with its
working directory set to your repository. On first run the image is built (this
provisions IDEasy + Claude Code and takes a few minutes); subsequent runs are
fast.

[TIP]
====
You can verify the setup without a running container engine. `--check` validates
the host and `--dry-run` prints the exact `docker run` command. Neither builds
the image nor starts a container:

[source,bash]
----
bash "$IDE_HOME"/settings/docker-sandbox/docker-sandbox.sh --check
bash "$IDE_HOME"/settings/docker-sandbox/docker-sandbox.sh --dry-run -- -p "fix the failing test"
----
====

== Options

The launcher supports the following options (see
`bash "$IDE_HOME"/settings/docker-sandbox/docker-sandbox.sh --help`):

[cols="30%,70%",options="header",grid="cols"]
|======================
| *Option* | *Description*
| `--repo <path>` | The git repository to mount (default: auto-detected from the
current directory via `git rev-parse --show-toplevel`).
| `--image <name>` | Image name (default: `ideasy-sandbox`).
| `--agent <name>` | The agent commandlet to run (default: `claude`).
| `--pull` | Rebuild the image before running.
| `--check` | Validate the host and exit (no build, no run).
| `--dry-run` | Print the exact `docker run` command and exit (no run).
| `--ca-cert <file>` | CA bundle to trust inside the container (`NODE_EXTRA_CA_CERTS`).
| `--api-key <value>` | Anthropic/Claude API key so the agent can authenticate inside the container
(shorthand for `--env ANTHROPIC_API_KEY=<value>`).
Also read from the host `IDEASY_SANDBOX_API_KEY` environment variable.
| `--env NAME=VALUE` | Extra environment variable for the agent, written into Claude's isolated config
at container start (repeatable). Use for a custom/proxy endpoint, e.g.
`ANTHROPIC_BASE_URL` and `ANTHROPIC_AUTH_TOKEN`.
| `--` | Forward everything after `--` to the agent.
|======================

Example - run a single prompt non-interactively, authenticated with an API key:

[source,bash]
----
bash "$IDE_HOME"/settings/docker-sandbox/docker-sandbox.sh --api-key "..." -- -p "run the failing test and fix it"
----

Example - point the agent at a custom/proxy Anthropic-compatible endpoint:

[source,bash]
----
bash "$IDE_HOME"/settings/docker-sandbox/docker-sandbox.sh \
  --env ANTHROPIC_BASE_URL="https://your-proxy.example" \
  --env ANTHROPIC_AUTH_TOKEN="Token_example" \
  -- -p "run the failing test and fix it"
----

Example - run a single prompt non-interactively:

[source,bash]
----
bash "$IDE_HOME"/settings/docker-sandbox/docker-sandbox.sh -- -p "run the failing test and fix it"
----

== Provisioning more tools

By default the image provisions `node` and `claude`. For projects that need
additional IDEasy tools (e.g. a JVM stack), build the image with the tools you
need (comma-separated, passed as `EXTRA_TOOLS`):

[source,bash]
----
docker build -t ideasy-sandbox --build-arg EXTRA_TOOLS="java,mvn" "$IDE_HOME"/settings/docker-sandbox
----

You can also point the sandbox at your own settings fork to layer in
project-specific tools and variables (passed as `IDE_SETTINGS_REPO`):

[source,bash]
----
docker build -t ideasy-sandbox \
  --build-arg IDE_SETTINGS_REPO="https://github.com/you/ide-settings.git" \
  "$IDE_HOME"/settings/docker-sandbox
----

For reproducible builds pin the IDEasy release with `IDEASY_VERSION` (see the
`ARG` declarations at the top of the `Dockerfile`).

== Git identity and security

* **Your Git identity is passed into the container** via
  `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME` and
  `GIT_COMMITTER_EMAIL` (read from your host `git config`), so commits created
  inside the sandbox use your local Git author and committer information.
* **The host SSH keys and SSH agent are NOT mounted into the container.**
  Mounting SSH keys would expose broad SSH access rights to the sandbox.

.Agent authentication (API key)
****
By default the agent has *no* credentials. To let it authenticate, pass an
Anthropic/Claude API key with `--api-key <value>` (or the host
`IDEASY_SANDBOX_API_KEY` environment variable). The launcher forwards it into
the container under a neutral name and the container entrypoint writes it into
Claude's isolated config (`$IDE_ROOT/sandbox/conf/claude/settings.json` →
`env.ANTHROPIC_API_KEY`). That location is deliberate: IDEasy scrubs ambient
`ANTHROPIC_*` environment variables out of the agent's environment, so the key
must be provided through Claude's own `settings.json`, which it applies itself.

The key is **never baked into the image** (a secret in image layers would be a
leak) and lives only in the container-local config, so it is discarded on exit
(`--rm`). It is also kept out of the process argument list (`ps`) - the
entrypoint reads it from the environment, not argv.
****

.Pushing and opening PRs
****
Because no credentials are mounted, **pushing branches or opening pull requests
from inside the container is an explicit, opt-in concern** you control. Typical
options, all of which keep secrets out of the shared host environment:

* Pass a scoped *GitHub personal access token* into the container (e.g. as an
  `ANTHROPIC`-unrelated environment variable or via the agent's own config) and
  have the agent push over `https` with that token.
* Use a CI/agent-provided token (e.g. `gh` authentication) scoped to the single
  repository.

Choose whichever fits your project. The default behavior is *no* network
credential is available - the agent can edit and commit locally, but not push,
until you explicitly provide a scoped credential.
****

== Manual test guide

[NOTE]
====
*Audience:* a technically skilled user verifying the sandbox on their own machine.

*Prerequisites* - A running container engine (Docker / Rancher Desktop /
Podman); `git` with a configured `user.name` / `user.email`; a checkout of the
repository; and a fresh agent credential (API key or token). On *Windows*, run
everything from WSL.

*Security:* replace every `<TOKEN>` / `<ENDPOINT>` below with your own values.
Never paste a live token into a file you commit.
====

=== Step 0 — Prerequisites (once)

[source,bash]
----
# 1. Engine is up
docker info >/dev/null && echo "engine OK" || echo "ENGINE NOT RUNNING"

# 2. Host Git identity (the launcher reads these to attribute commits)
git config user.name
git config user.email

# 3. (First time only) build the image — provision IDEasy + node + claude
cd <wsl-path>/workspaces/main/IDEasy
bash "$IDE_HOME"/settings/docker-sandbox/docker-sandbox.sh --pull
----

*PASS:* `engine OK`, a name/email are printed, and the build finishes
without `failed` / `error` lines.

=== Step 1 — Validate the host, no container started

[source,bash]
----
cd <wsl-path>/workspaces/main/IDEasy
bash "$IDE_HOME"/settings/docker-sandbox/docker-sandbox.sh --check
----

* *Purpose:* check engine + Dockerfile + git identity.
* *PASS:* prints `Check passed. (No image was built or started.)`
* Works even when the engine is stopped.

=== Step 2 — Preview the exact `docker run` (no container started)

[source,bash]
----
bash "$IDE_HOME"/settings/docker-sandbox/docker-sandbox.sh --dry-run -- -p "reply with the single word: hello"
----

* *Purpose:* review the command the launcher will run.
* *PASS:* it prints a `docker run` line containing
`-v <repo>:...`, `-w ...`, and the agent `claude`. No container
is started.

=== Step 3 — End-to-end round-trip (the critical test)

This is the single most important check: it proves the agent runs,
credentials are injected, and the corporate CA is trusted.

[source,bash]
----
cd <wsl-path>/workspaces/main/IDEasy

CA="$HOME/.ide/ca.pem"   # local (git-ignored) CA bundle for the internal proxy

docker run --rm --init \
  -e NODE_EXTRA_CA_CERTS=/etc/ssl/ideasy-ca/ca-bundle.pem \
  -e IDEASY_SANDBOX_E_ANTHROPIC_BASE_URL="https://<ENDPOINT-COMPANY>" \
  -e IDEASY_SANDBOX_E_ANTHROPIC_AUTH_TOKEN="<YOUR-TOKEN>" \
  -e IDEASY_SANDBOX_E_ANTHROPIC_MODEL=code \
  -v "${CA}:/etc/ssl/ideasy-ca/ca-bundle.pem:ro" \
  -w /projects/sandbox/workspaces/main \
  ideasy-sandbox:latest claude -p 'Reply with exactly the single word: hello'
----

*How to read the output:*

[width="100%",cols="50%,50%",options="header",]
|===
|You see |Meaning
|`[ideasy-sandbox] Applied to ...: ANTHROPIC_MODEL, ANTHROPIC_AUTH_TOKEN, ANTHROPIC_BASE_URL`
|credential injection works

|*No* `warn: ignoring extra certs ... Is a directory` |CA bundle loads
correctly

|*No* `Self-signed certificate detected` |corporate CA is trusted

|`hello` on the last line |*agent runs and calls the API successfully*

|`unrecognized_model "code"` |non-blocking warning (session-title
only) — ignore
|===

*PASS:* you get `hello` and there is no certificate error.

[TIP]
====
Do *not* use `-i -t` in a non-interactive (CI/script) context — it fails
with `cannot attach stdin to a TTY-enabled container`. Use the `-p` form
above.
====

=== Step 4 — Lifecycle + `docker exec` (keep-alive)

[source,bash]
----
# Keep the container running so you can inspect it
docker run -d --init --name sbx \
  -e IDEASY_SANDBOX_E_ANTHROPIC_BASE_URL="https://<ENDPOINT>" \
  -e IDEASY_SANDBOX_E_ANTHROPIC_AUTH_TOKEN="<YOUR-TOKEN>" \
  ideasy-sandbox:latest keep-alive

docker exec -it sbx bash

#   inside the container:
claude                       # start the interactive agent
docker exec sbx ls -la /etc/ssl/ideasy-ca/
docker exec sbx cat /projects/sandbox/conf/claude/settings.json | sed 's/sk-[A-Za-z0-9]*/<hidden>/g'
docker exec sbx printenv | grep -E '^(ANTHROPIC|IDEASY_SANDBOX)' | sed 's/sk-[A-Za-z0-9]*/<hidden>/g'

# Tear down
docker rm -f sbx
----

* *PASS:* you can enter the container; `settings.json` has an `env`
block with the endpoint/token; the CA is a *file* (not a directory); the
token is not leaked in plain text in the config you inspect.

=== Step 5 — Isolation (the core quality property)

Goal: prove the agent edits *only* the real repo and does *not* touch
the host IDEasy installation.

[source,bash]
----
# 1. Seed a scratch file in the repo
echo "test-line-before" > <repo>/sandbox-test.txt
git status                    # note the before-state

# 2. Ask the agent to modify it
docker run --rm --init \
  -e IDEASY_SANDBOX_E_ANTHROPIC_BASE_URL="https://<ENDPOINT>" \
  -e IDEASY_SANDBOX_E_ANTHROPIC_AUTH_TOKEN="<YOUR-TOKEN>" \
  -w /projects/sandbox/workspaces/main/IDEasy \
  ideasy-sandbox:latest claude -p 'Append the text "sandbox-ran" to the file sandbox-test.txt. Do not commit.'

# 3. Verify on the HOST (the real repo)
git status                    # sandbox-test.txt shows as modified
cat <repo>/sandbox-test.txt   # contains "sandbox-ran"
git diff

# 4. Verify the host IDEasy runtime is untouched
#    conf/ and software/ of your host workspace must be unchanged
----

* *PASS:* the file on the host was modified by the agent, while the host
`conf/` and `software/` are unchanged.
* *Cleanup:* `git checkout -- sandbox-test.txt` (or delete the file).

=== Step 6 — `--api-key` path (alternative credential path)

[source,bash]
----
export IDEASY_SANDBOX_API_KEY="<YOUR-TOKEN>"
bash "$IDE_HOME"/settings/docker-sandbox/docker-sandbox.sh -- -p "reply with the single word: ok"
----

* *PASS:* you get `ok`. Confirms the `--api-key` /
`IDEASY_SANDBOX_API_KEY` shorthand works, not only the
`--env` path.

=== Test checklist

[width="100%",cols="12%,24%,64%",options="header",]
|===
|# |Test |Pass condition
|0 |Prereqs + image build |`engine OK`, identity present, build
clean

|1 |`--check` |`Check passed`

|2 |`--dry-run` |command printed, nothing started

|3 |*E2E + proxy + CA* |gets `hello`, no cert error

|4 |keep-alive + `exec` |enter container, config/cert/env correct

|5 |Isolation |agent edits the real repo, host IDEasy unchanged

|6 |`--api-key` |gets `ok`
|===

Step 3 is the gating test: if it passes, the rest confirm quality and
security.

== Troubleshooting and limitations

* **No container engine / engine stopped:** start your container engine (e.g.
  Rancher Desktop). `--check` and `--dry-run` still work without a running daemon.
* **Windows:** run from WSL (a Docker-compatible Linux container environment);
  see the *Testing Linux on Windows* section of the contributing documentation.
* **First run is slow:** the initial build provisions IDEasy + the agent. Use
  `--pull` only when you intentionally want to rebuild.
* **`claude` cannot authenticate:** pass an API key with `--api-key <value>` (or
  the host `IDEASY_SANDBOX_API_KEY` env var). Do not rely on ambient host
  secrets, which are not present in the container - IDEasy deliberately scrubs
  them (see the *Agent authentication* note).
* **Cleanup:** the container is started with `--rm`, so the container-local
  IDEasy runtime is discarded on exit. Only your bind-mounted repository (and any
  commits/pushes you performed) remain on the host.

.Common issues

[width="100%",cols="50%,50%",options="header",]
|===
|Symptom |Likely cause / fix
|`cannot attach stdin to a TTY-enabled container` |You used `-i -t`
without a TTY. Use the `-p` form (Step 3).

|`Self-signed certificate detected` |The CA bundle is missing or wrong.
Rebuild it from the endpoint chain (intermediate + root) and
re-verify with `openssl verify -CAfile <bundle> <leaf>`
→ `OK`.

|Agent cannot authenticate |Credentials not passed. Use `--api-key` or
`--env ANTHROPIC_AUTH_TOKEN=...`; IDEasy scrubs ambient
`ANTHROPIC_*` variables, so they must be injected at start.

|Windows path errors in `docker run` |Run from WSL; keep container paths
Unix-style.

|`unrecognized_model` warning |Non-blocking. Clear by mapping the
model via `behavesAs` / `modelOverrides` in the settings repo.
|===
